# 企业知识库：图片的索引和检索技术落地方案

## 1. 概述

企业知识库里的图片就两个来源，处理方式不一样：

- **独立图片文件**：产品图、缺陷照片、现场拍摄、扫描件；
- **文档里的插图**：手册里的接线图、PPT 截图、报告里的示意图。

举例：用户问“接线图在手册哪一页”。

## 2. 图片转文字 OR 图文向量

**一，图片转文字。** 图片走光学字符识别(OCR)，加上原文里的图注、必要时再用模型生成一段画面描述，产出的是带页码和坐标的文本块，直接进现有的文本索引。便宜、可解释、天然带出处，不需要额外的向量空间。

**二，做图文向量。** 图片和文本进同一个语义空间，直接以文搜图、以图搜图。需要多模态(Multimodal)向量模型，成本和复杂度都更高。

**可以尝试先做一，按需要再加二。** 

企业图片里信息密度最高的是图上的文字——工程图的标注、截图上的菜单、扫描件的正文，OCR 加图注就能定位到位，而且答案天然能给出页码。

真正非做图文向量不可的，是“找和这张图相似的产品图或缺陷图”这类以图搜图需求。

这是经验判断，不是普适结论。

反过来的情况也很明确：如果图片本身没什么文字、也没人写图注（比如纯外观照片、缺陷图库），路线一抓不到东西，那就得直接上路线二。

## 3. 图片怎么抽出来

**1 独立图片文件**

直接进对象存储，元数据(Metadata)靠人工或业务系统补。

**2 文档里的插图**

要靠解析工具抽。用 MinerU（OpenDataLab 开源，PDF/PPT 解析）时有个取法上的讲究：

**3 要取它的中间态 JSON，不要只取 Markdown。** 

JSON 里带每张图的页码、坐标和类型，Markdown 输出把这些全丢了——丢了就做不了“跳回原文第几页那张图”，出处直接落空。

**4 过滤装饰图。** 

解析工具会把页眉图标、logo、分隔线、装饰底纹一并抽出来，量还不小。

这些图全量向量化既费钱又污染召回结果——用户搜“接线图”，结果里混进十几个 logo。按尺寸下限、宽高比、在页面中的位置和重复出现次数做一遍过滤，这一步的收益比调模型大。

**5 继承父文档的权限和版本。** 

图是从文档里抽出来的，它的权限标签、版本号、有效状态必须跟着父文档走。漏了这一步就会出现文档本身有权限控制、抽出来的图却裸奔的情况。

## 4. 一张图存成什么

图片的内容块可以参考下面的字段：

```text
chunk_id          这张图的唯一标识
document_id       所属文档
version_id        所属版本
parent_id         图所在的章节或知识单元
chunk_type        固定为 image
image_uri         原图在对象存储的地址
page_no           页码（来自文档的图才有）
bbox              图在页面中的坐标
ocr_text          图上识别出的文字
caption           原文里的图注
description       模型生成的画面描述（可选）
metadata          继承自父文档的权限、版本、产品等过滤字段
```

`ocr_text`、`caption`、`description` 三段拼起来就是这张图的可检索文本，走图片转文字时索引的就是它们。

`page_no` 加 `bbox` 是出处的落点——**出处要落到位置，不是落到文件名**，用户点开要能直接看到那一页的那张图。

## 5. 技术选型

### 5.1 商用API

这一档是传文件就能问，解析、切分、向量化、检索全内置。

**火山引擎 VikingDB 知识库**支持 pdf、ppt、doc、txt、markdown、xlsx、csv、jsonl、faq、mp4 等格式，内置文档解析和切片（默认按语义均衡切片，也可自定义规则）。图片这块，**OCR 是一个可选开关**，开启后对 pdf、docx 里的图片做文字识别；检索侧提供多模态检索（文搜图、图搜图）和图文问答。

**阿里云 OpenSearch LLM 智能问答版**是一站式开箱的 RAG 方案，内置非结构化数据处理、向量模型、文本与向量检索和大模型，支持从 PDF、Word、表格、图片文档里检索；另有多模态 RAG 能力，能解析图片内容再结合生成回答。

注意的是数据要出内网，解析和切分只能用第三方厂商的那几种策略。

### 5.2 开源 RAG 框架，私有化部署

数据不能出内网就走这档，同样不用自己写管线：

- **RAGFlow**：强在细粒度文档解析，模块化设计，OCR 模型和检索算法都能替换——图片这块要动手调，它的可改造空间更大。
- **Dify**：强在工作流编排和混合检索，召回模式丰富，适合要把检索接进更复杂业务流程的场景。

两个也常组合：Dify 做编排和界面，RAGFlow 做文档解析。

### 5.3 C 档：自己拼组件

只有 A、B 都满足不了才走这档。典型情况是：以图搜图是核心需求而现成产品的图片能力不够、图必须和页面坐标严格绑定、或者装饰图过滤规则复杂到框架里塞不进去。

**商用向量 API。** 以下是截至 2026 年 7 月公开文档上的信息，具体参数以官方文档为准。

**火山引擎**把向量化(Embedding)和向量检索打包在 VikingDB 里，图片相关的两个模型：

- `doubao-embedding-vision`：文本和图片进同一空间。250615 版 2048 维（可降到 1024），241215 版 3072 维。输入接受 TOS 路径、http(s) 链接或 base64。
- `bge-visualized-m3`：文本和图片，1024 维，支持单独编码或图文联合编码。它本身是开源模型，以后想从商用切回自建，向量不用重算——这点在选型时值得考虑。

检索侧有多模态检索接口（SearchByMultiModal），支持向量与标量混合过滤，也就是能先按权限和版本圈定范围再做近邻检索。

**阿里云**是模型和向量库分开的。

百炼（Model Studio）提供多模态向量 API，

可选 `multimodal-embedding-v1`、`tongyi-embedding-vision-plus`、`tongyi-embedding-vision-flash`，

基于 Qwen2-VL 训练，文本和图像落在同一语义空间，支持以文搜图、以图搜图。

向量存储再接 DashVector、Milvus 版或 OpenSearch 向量检索版。它还区分“独立向量”和“融合向量”：图文分别出向量，还是图文合成一个向量，取决于要逐项比对还是整体匹配。

区别是：

**火山把向量化和向量库打包了，链路短；阿里云更松耦合，模型和存储各选各的。** 

只想尽快跑通就前者省事，向量库已经定了或者要跨云就后者更灵活。

官方文档：[VikingDB embedding v2](https://www.volcengine.com/docs/84313/1254554)、[百炼 Multimodal-Embedding API](https://help.aliyun.com/zh/model-studio/multimodal-embedding-api-reference)。

**开源组件。** 全链路私有化时，零件也都是现成的：

| 能力 | 可选组件 |
|---|---|
| 中文图文向量 | Chinese-CLIP（达摩院开源）、bge-visualized-m3、SigLIP |
| 图上的文字 | PaddleOCR |
| 画面描述 | Qwen2.5-VL、InternVL 等开源视觉语言模型(Vision-Language Model, VLM) |
| 向量库 | Milvus、Qdrant、pgvector、Elasticsearch |

也可以混着来：OCR 量大、本地跑便宜，用开源；图文向量模型效果差距明显，用商用 API。数据分级的场景里这种组合比较常见。

### 5.4 关于图片，这里有句实话

A 档和 B 档标称的“支持图片”，**多数停在 OCR 这一层**，也就是第 2 节的路线一。对大部分企业场景这够用了。

但如果你要的是路线二的以图搜图，现成产品的支持程度参差不齐，选型时必须**拿自己的图实测一遍**，别看功能列表勾了几个。这是最可能把你从 A、B 档逼到 C 档的地方，也是唯一值得提前花时间验证的点。

## 6. 检索怎么走

**以文搜图**有两条路，取决于第 2 节选了哪条路线：走路线一，就是拿文本 query 去检索图片的 `ocr_text` 加 `caption` 加 `description`，本质还是文本检索；走路线二，是文本和图片在同一空间里做近邻检索。两条可以同时开，再融合。

**以图搜图**只有路线二能做：用户传一张图，出向量，检索图向量索引。

不管哪条，**过滤都要在召回之前**。权限、版本、有效状态、产品范围先把范围圈出来，再做近邻检索——这不是“缩小范围”的优化，是质量闸门，无权的图一张都不能漏进召回池。用 VikingDB 这类支持标量过滤的向量库，可以在检索时直接带条件；自建 Milvus 就要把过滤字段冗余一份到标量列上。

**返回时要带位置**：文档名、版本、页码、图在页面上的位置，以及原图入口。用户要能点回去核实。

## 7. 几个会真卡住的地方

**向量空间不通用，不能混检。** 这条最容易踩：只有同一个模型产出的图向量和文本向量才在同一空间，才能直接以文搜图。如果图片用 Chinese-CLIP、文本用 bge，两套向量不在一个空间，**不能放进同一个索引比距离**，必须分开建索引、各自召回，再在融合层合并（BM25 分数和向量距离量纲不同，只能按排名融合）。

**OCR 和图注常常比向量更管用。** 工程图、界面截图、扫描件，关键信息就在图上的字里。别一上来就堆多模态模型，先把 OCR 做扎实，很多场景到这就够用了。

**装饰图不过滤，召回质量会被拖垮。** 见第 3 节。这一步做不做，比换哪个 embedding 模型影响大。

**成本主要在图片总量上。** 文档里抽出来的图数量往往比预估的多一个量级，全量向量化前先估一遍量，并且先过滤再向量化，别反过来。

**没有文字的图，路线一直接失效。** 纯外观照片、缺陷图这类，OCR 抓不到东西、也没人写图注，只能靠 VLM 生成描述或者直接上图文向量。入库前先抽样看一眼图片里到底有没有字，这个判断决定路线。
