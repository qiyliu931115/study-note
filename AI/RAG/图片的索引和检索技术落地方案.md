## 1. 概述

本文说明知识库中图片的入库与检索方案。

企业知识库中的图片有两类来源，处理方式不同：

- **独立图片文件**：产品图、缺陷照片、现场拍摄、扫描件；
- **文档内插图**：手册中的接线图、PPT 截图、报告中的示意图。

第二类通常数量更多，价值也更高。典型的检索需求是定位到具体位置，例如“接线图位于手册第几页”，而非查找视觉上相似的图片。

## 2. 技术路线：图片转文字与图文向量

图片入库有两条技术路线，需要在方案设计阶段先行确定。

**图片转文字。** 对图片执行光学字符识别(OCR)，结合原文图注，必要时由模型生成画面描述，产出带页码和坐标的文本块，进入既有的文本索引。成本低、结果可解释、天然携带出处，不需要额外的向量空间。

**图文向量。** 图片与文本映射到同一语义空间，支持以文搜图和以图搜图。需要多模态(Multimodal)向量模型，成本和复杂度更高。

**建议先实施图片转文字，再按需要叠加图文向量。** 企业图片中信息密度最高的部分是图上的文字——工程图的标注、界面截图的菜单、扫描件的正文，OCR 结合图注即可完成定位，且答案天然带页码。仅当存在“查找与某张图相似的产品图或缺陷图”这类以图搜图需求时，图文向量才是必需的。

以上为经验判断，不构成普适结论。反向情形同样明确：若图片本身文字很少、也缺少图注（例如纯外观照片、缺陷图库），图片转文字无法提取到有效信息，应直接采用图文向量。

## 3. 图片的提取与预处理

**独立图片文件**直接进入对象存储，元数据(Metadata)由人工或业务系统补充。

**文档内插图**需要解析工具提取。使用 MinerU（OpenDataLab 开源，负责 PDF/PPT 解析）时，应取其中间态 JSON 而非 Markdown 输出：JSON 保留每张图的页码、坐标和类型，Markdown 会丢失这些信息，导致无法定位到原文中的具体位置，出处随之失效。

提取之后有一项处理不可省略。

**文档内容清洗**

页眉图标、logo、分隔线、水印、装饰底纹没有检索价值，若进入索引会占用向量化成本，并在召回时与有效图片竞争。

第一道过滤直接使用解析器的版面分类结果，而非自行编写规则。MinerU 基于 DocLayoutYOLO 做版面分析，会为每个区块标注类型：

正文图片为 `image_body`，图注为 `image_caption`，而页眉、页脚、页码归入 abandon 类（VLM 后端对应 `header`、`footer`、`page_number`）。

页眉位置的 logo 多数落在 abandon 类，默认不会作为 `image_body` 输出。也就是说，大部分页面装饰在解析阶段已被分离，无需额外处理。

真正会漏入 `image_body` 的是版面模型分错的部分：铺满整页的水印和背景图、出现在正文区域而非页眉的 logo。对这部分，常见的补充手段是两条轻量规则：

- **尺寸与面积占比**：过小（图标）或接近整页（背景、水印）的图片按阈值剔除；
- **哈希去重**：同一张 logo 在多页中字节完全相同，按哈希归并，既省去重复向量化，也避免同一张图占满召回结果。

训练分类模型、按文档来源配置白名单等做法确实存在，但成本较高，多数知识库并不需要——版面分类加上述两条规则通常已能将噪声压到可接受范围。仅当图片检索质量直接影响业务（见 5.3 的场景）时，才值得投入训练分类器。人工在此环节的现实角色是在调整阈值阶段抽查若干页、确认规则未误删有效图，而非对全量图片逐张审核或长期维护白名单。

反向误删同样存在：版面模型偶尔会将有效插图判为 abandon。若召回结果明显缺图，应回到解析环节检查分类，而非在下游反复调整向量模型。

## 4. 图片内容块的字段

图片的内容块可参考以下字段：

```text
chunk_id          这张图的唯一标识
document_id       所属文档
version_id        所属版本
parent_id         图所在的章节或知识单元
chunk_type        固定为 image
image_uri         原图在对象存储的地址
page_no           页码（来自文档的图才有）
bbox              图在页面中的坐标
ocr_text          图上识别出的文字
caption           原文里的图注
description       模型生成的画面描述（可选）
metadata          继承自父文档的权限、版本、产品等过滤字段
```

`ocr_text`、`caption`、`description` 三段合并即为该图片的可检索文本，采用图片转文字方案时索引的就是这部分内容。

`page_no` 与 `bbox` 是出处的落点——**出处应定位到位置，而非文件名**，用户点击后需要直接看到对应页面中的对应图片。

## 5. 技术选型

实现方式按自建程度分为三层，优先采用上层方案，上层无法满足时再向下选择。

### 5.1 商用 API

商用 API传入文件即可使用，解析、切分、向量化、检索均已内置。

**火山引擎 VikingDB 知识库**支持 pdf、ppt、doc、txt、markdown、xlsx、csv、jsonl、faq、mp4 等格式，内置文档解析与切片（默认按语义均衡切片，也支持自定义规则）。图片方面，OCR 为可选开关，开启后对 pdf、docx 中的图片执行文字识别；检索侧提供多模态检索（文搜图、图搜图）和图文问答。

**阿里云 OpenSearch LLM 智能问答版**是一站式开箱的 RAG 方案，内置非结构化数据处理、向量模型、文本与向量检索和大模型，支持从 PDF、Word、表格、图片文档中检索，并具备多模态 RAG 能力，可解析图片内容后结合生成回答。

商用 API的约束是数据需要出内网，且解析与切分只能使用厂商提供的策略。

### 5.2 开源 RAG 框架

- **RAGFlow**：细粒度文档解析能力较强，模块化设计，OCR 模型与检索算法均可替换，图片处理的可改造空间更大。

### 5.3 引用组件自建功能

仅在 5.1 和 5.2 均无法满足时采用。典型情况有三类：

- **需要用图片作为查询输入。** 例如现场工程师拍下设备铭牌或故障部位的照片，系统据此找到同型号的历史工单和维修方案；或质检人员拍下缺陷照片，检索历史上同类缺陷的处理记录。商用知识库多数只提供上传文档的入口，查询侧仍是文本框，不接受图片作为 query。
- **回答需要定位到页面中的具体区域。** 例如审计或法务场景要求在 PDF 原文上高亮出作为依据的那张图，而不只是给出页码。多数框架只返回文本片段和页码，不透出图片的 `bbox` 坐标，前端无法在页面上画出位置。
- **装饰图过滤规则需要按来源区分。** 不同厂商手册的 logo 位置和尺寸各不相同；部分图片（例如带型号标识的产品外观图）既是模板元素又携带信息，不能一概过滤。这类需求要按文档来源配置不同规则，或引入分类模型判断图片是否有效。框架侧通常只提供“是否解析图片”这类开关，无法承载这一粒度的规则。

该层提供的是单个能力的接口，各环节之间的衔接需要自行实现。

**组件的分工与顺序。** 以 MinerU、向量模型、Milvus 三者为例，它们是流水线上的三道工序，顺序由各自的输入输出类型决定：

| 组件 | 输入 | 输出 | 职责 |
|---|---|---|---|
| MinerU | PDF / PPT 文件 | 内容块（文字、图片）+ 页码 + bbox | 把文件拆成可处理的内容块 |
| 向量模型 | 单块内容（一段文字或一张图） | 向量（一组浮点数） | 把内容转为可比较距离的数值表示 |
| Milvus | 向量 + 标量字段 | top-k 相似结果 | 存储向量并按距离检索 |

数据形态的变化过程：

```text
PDF 手册
  ↓ MinerU
第 28 页的一张接线图 + bbox(120,340,480,620)
  ↓ 向量模型
[0.021, -0.183, 0.077, ...]  共 1024 维
  ↓ Milvus
存入并建立索引，可被检索
```

顺序不可调换的原因有三点：Milvus 只接受向量，PDF 和中文文本都无法直接写入，中间必须有向量模型；向量模型一次只处理一块内容，整个 PDF 文件无法作为输入，前面必须先由 MinerU 拆分；MinerU 只负责解析、不产出向量，Milvus 只负责存储检索、不解析文件，两端都无法替代中间环节。

**向量模型在入库和检索两侧各调用一次，且必须是同一个模型：**

```text
入库侧    图片      → 向量模型 → 向量 → 写入 Milvus
检索侧    查询文本  → 向量模型 → 向量 → 与库中向量比对
```

Milvus 执行的操作只是比较两个向量之间的距离。若入库使用模型 A、检索使用模型 B，两组向量不在同一坐标系中，得到的距离没有意义——检索仍会正常返回结果且不报错，但结果是错乱的。这是该层最隐蔽的故障点。

**数据的存放位置。** 一张图片的数据分布在三处，向量化只是其中一环：

| 位置 | 存放内容 |
|---|---|
| 对象存储（MinIO、OSS、TOS） | 原图文件 |
| 向量库（Milvus 等） | 向量、chunk_id、用于过滤的标量字段 |
| Elasticsearch 或关系库 | chunk 完整记录：`ocr_text`、`caption`、`page_no`、`bbox`、元数据 |

向量库中不存原图，只保留指回原图的地址。一条记录的实际形态：

```text
id           chunk_a1b2
vector       [0.021, -0.183, 0.077, ...]   共 1024 维
image_uri    oss://kb/manual-v3.2/p28-img1.png
document_id  doc_1001
page_no      28
version      V3.2
status       现行
acl          ["售后技术"]
```

`vector` 之后的字段均为标量字段，作用是在近邻检索时直接附加过滤条件，避免先查询其他系统再传入候选 ID 列表。

**检索的执行过程。** 以文搜图为例：

```text
1. 用户输入“配电柜接线图”
2. 用与图片入库时相同的模型，将该文本转为向量
3. 在向量库执行近邻检索，同时附加权限、版本、状态过滤条件
4. 返回 top-k 的 chunk_id 与相似度分数
5. 用 chunk_id 回查完整记录，得到 image_uri、page_no、bbox
6. 从对象存储取回原图，连同文档名和页码一并返回
```

对应的调用形态：

```python
q_vec = embed_text("配电柜接线图")      # 与图片入库使用同一模型
hits = milvus.search(
    collection_name="kb_images",
    data=[q_vec],
    limit=10,
    filter='status == "现行" and version == "V3.2"',
)
# hits -> [(chunk_a1b2, 0.83), (chunk_c3d4, 0.79), ...]
```

以图搜图的流程相同，仅第 2 步改为将用户上传的图片转为向量。

第 2 步必须使用与入库侧相同的模型，原因见前文“向量模型在入库和检索两侧各调用一次”。


### 5.4 图片能力的实际边界

商用 API 与开源框架标称的“支持图片”，多数停留在 OCR 层面，即第 2 节的图片转文字。对大部分企业场景，这一能力已经够用。

若需求为路线二的以图搜图，现成产品的支持程度差异较大，选型阶段应使用实际业务图片进行验证，不能仅依据功能列表判断。这是最可能迫使方案退回引用组件自建功能的环节，也是唯一值得提前投入时间验证的点。

## 6. 检索流程

**以文搜图**有两种实现，取决于第 2 节确定的路线。路线一是用文本 query 检索图片的 `ocr_text`、`caption` 和 `description`，本质仍是文本检索；路线二是文本与图片在同一空间中执行近邻检索。两者可同时启用后融合。

**以图搜图**仅路线二可实现：用户上传图片，生成向量后检索图向量索引。

无论采用哪种实现，**过滤都必须在召回之前执行**。权限、版本、有效状态、产品范围先圈定范围，再执行近邻检索。这不是缩小范围的优化项，而是质量闸门，无权限的图片不能进入召回池。使用 VikingDB 这类支持标量过滤的向量库时，可在检索时直接附加条件；自建 Milvus 则需要将过滤字段冗余至标量列。

**返回结果应携带位置信息**：文档名、版本、页码、图片在页面中的位置，以及原图入口，以便回溯核实。

## 7. 主要风险点

**向量空间不通用，无法混合检索。** 只有同一模型产出的图向量与文本向量位于同一空间，才能直接以文搜图。若图片使用 Chinese-CLIP、文本使用 bge，两套向量不在同一空间，不能置于同一索引中比较距离，必须分别建立索引、各自召回，再在融合层合并（BM25 分数与向量距离量纲不同，只能按排名融合）。

**OCR 与图注的作用通常大于向量。** 工程图、界面截图、扫描件的关键信息都在图上的文字中。多数场景下先完善 OCR 环节即可满足需求，不必在初期引入多模态模型。

**装饰图未经过滤会显著降低召回质量。** 成因与过滤方法见第 3 节。该步骤的收益高于更换向量模型。

**成本主要取决于图片总量。** 文档中提取出的图片数量通常比预估高一个量级，全量向量化前应先估算规模，并遵循先过滤、后向量化的顺序。

**缺少文字的图片会使路线一失效。** 纯外观照片、缺陷图这类内容，OCR 无法提取有效信息，也缺少图注，只能依靠 VLM 生成描述或直接采用图文向量。入库前应抽样确认图片中是否含有文字，该结论直接决定路线选择。
