# 企业知识库：非结构化数据的录入与检索

本文说明企业知识库中的非结构化数据如何录入和检索。核心方法是：录入时保存原文件，保真解析内容，补充完整元数据，建立父子知识块和多种索引；检索时先执行权限及有效性闸门，再过滤、混合检索、回溯上下文，并返回可核验的出处。

## 1. 什么是非结构化数据

非结构化数据是指内容主要以自然语言、图像或音视频形式存在，不能直接按照固定字段进行查询和计算的数据。

典型来源包括：

- Word、PDF、PPT 等文档；
- 图片、扫描件；
- 录音、视频；
- 产品手册、制度文件、会议纪要、项目报告。

这里所说的“非结构化”，并不表示内容内部完全没有结构。文档可能包含标题、章节、表格和图片，只是这些结构不像数据库字段那样统一、稳定，通常需要经过解析后才能用于检索。

## 2. 录入流程

非结构化数据的基本录入流程是：

```text
保存原文件
→ 按内容类型解析
→ 补充完整元数据（包括版本和有效状态）
→ 建立父子分块
→ 建立全文、向量及必要的多模态索引
```

### 2.1 保存原始文件

首先保留未经修改的原文件，原因包括：

- 用户需要查看和核对原文；
- 解析结果可能存在错误；
- 更换解析工具后可以重新处理；
- 回答需要引用原始页码、章节或时间点；
- 原文件中的版式、图片和表格关系无法完全由纯文本表达。

知识库不能只保存解析后的文本，否则会失去重新处理和核验内容的基础。

### 2.2 特别管理版本及有效状态

版本和有效状态属于元数据的一部分，完整字段统一在 2.4 节定义。这里单独强调它们，是因为这些信息必须直接用于 3.1 节的有效性闸门，而不能只作为普通的检索提示。

旧文档可以保留用于历史追溯，但不能与现行文档平等参与默认检索。系统需要根据版本、状态、生效与失效时间以及版本取代关系，判断一份文档能否用于回答当前问题。

### 2.3 按内容类型解析

不同类型的内容应采用不同的处理方式：

| 内容 | 处理方式 |
|---|---|
| 可复制文字的 Word/PDF | 提取文字、标题和章节结构 |
| 扫描 PDF、图片 | 进行光学字符识别（OCR），并保留页面坐标 |
| 表格 | 保留表头、行列关系和合并单元格 |
| 图片 | 保留原图，并生成标题、说明或内容描述 |
| 流程图 | 尽量提取节点、连接关系和流程说明 |
| 录音 | 转写文字，并关联原始时间点 |
| 视频 | 提取语音、字幕和关键画面，并关联时间点 |

解析结果必须能够回到原始位置，例如 PDF 页码、文档章节、图片位置或音视频时间点。

#### 表格不能退化成普通文本

表格应保留双重表示：

```text
结构化的行列数据
+
便于全文或语义检索的文字说明
```

如果直接把表格拉平成一行文字，表头与单元格之间的对应关系就可能丢失，导致“V3.2 的额定电流是多少”一类问题无法准确回答。

#### 图片和流程图需要可检索表示

在纯文本检索链路中，图片至少需要标题、图注或人工/模型生成的内容描述。支持多模态能力时，也可以同时建立图像向量索引。

### 2.4 补充完整元数据

非结构化内容本身缺少统一字段，因此录入时需要补充完整元数据。本文涉及的元数据字段统一在这里定义：

```text
文档名称
文档类型
所属业务
产品型号
适用版本
适用地区或组织范围
发布部门
作者
版本号
发布日期
生效日期
失效日期
当前状态（草稿、现行、废止）
被哪个版本取代
权限范围
原文件地址
```

这些元数据分别用于权限校验、有效性判断和检索范围过滤。其中版本号、发布日期、生效日期、失效日期、当前状态和版本取代关系共同为 3.1 节的有效性闸门提供判断依据。

### 2.5 建立父子分块

长文档不能整体作为一个检索单位，但也不能只按固定字数机械切割。更稳妥的方法是建立父子两层内容结构。

父块保存完整知识单元，例如：

```text
3.1 设备无法启动
```

子块保存语义更集中的内容，例如：

```text
故障现象
原因一：电源模块异常
原因二：保险丝熔断
处理步骤一
处理步骤二
```

检索主要针对子块，每个子块都要携带：

- 父块 ID；
- 文档 ID；
- 章节路径；
- 页码；
- 版本；
- 有效状态；
- 权限信息。

这样既不会因为块太大、语义混杂而降低匹配精度，也可以在命中子块后恢复完整章节。

### 2.6 建立检索索引

通常同时建立以下索引：

#### 全文索引

用于检索明确出现的内容，例如：

- 错误码；
- 产品型号；
- 部件名称；
- 制度条款名称；
- 专业术语。

#### 向量索引

用于检索表达不同但含义相近的内容。例如用户说“按下开关没有反应”，文档中写的是“设备无法启动”，语义检索可以将二者匹配起来。

#### 多模态索引

当知识库需要直接检索图片、流程图或视频画面时，可以建立图像或多模态向量索引。

因此，非结构化数据的录入结果可以概括为：

```text
原文件
+
解析后的内容
+
元数据和有效性信息
+
父子知识块
+
全文、向量及必要的多模态索引
```

## 3. 检索流程

非结构化数据的基本检索流程是：

```text
权限及有效性闸门
→ 元数据过滤
→ 子块混合检索
→ 结果排序
→ 父块上下文回溯
→ 返回带版本和出处的答案
```

### 3.1 先执行权限及有效性闸门

默认只允许以下文档参与回答：

- 用户有权查看；
- 已正式发布；
- 在查询时间点已经生效；
- 尚未失效；
- 未被更新版本取代；
- 适用于当前产品、地区或组织。

版本和生效状态不是普通的“缩小范围”条件，而是质量闸门。旧版本即使与问题高度相关，也不能默认用于回答当前问题。

如果用户查询历史政策，应根据指定时间检索当时有效的版本。如果必须引用旧版本，答案中需要明确提示：

> 以下内容来自 V2.0，该版本已废止，现行版本为 V3.2。

### 3.2 根据元数据缩小范围

从问题中识别以下条件：

- 所属业务；
- 产品型号；
- 适用版本；
- 文档类型；
- 发布时间；
- 适用地区或组织。

例如用户询问 V3.2 版本设备的故障处理方法，应先限定适用版本，避免召回其他版本的操作说明。

### 3.3 在子块上进行混合检索

不同内容采用不同的检索方式：

- 型号、错误码、条款名称：关键词或精确检索；
- 自然语言描述：向量语义检索；
- 文档类型、版本、产品范围：元数据过滤；
- 表格问题：优先检索保留行列关系的表格数据；
- 图片或流程问题：检索图片描述或多模态索引。

关键词检索与向量检索通常应结合使用，不能只依赖其中一种。

### 3.4 对结果排序并回溯父块

系统首先对命中的子块进行相关性重排，优先考虑产品和版本是否一致、关键词与语义相关度是否足够，以及适用范围是否匹配。排序完成后，再沿父子关系取回完整上下文，例如：

- 故障现象；
- 相关原因；
- 完整操作步骤；
- 注意事项；
- 关联表格或图片。

这种方式比临时抓取相邻文本更稳定，因为上下文关系已经在录入阶段明确保存。

### 3.5 返回带出处的答案

最终答案应尽量提供：

- 文档名称；
- 当前版本；
- 章节；
- 页码；
- 生效状态；
- 原文入口。

用户不仅能够获得答案，还能回到有效原文进行核实。

## 4. 完整示例

用户询问：

> V3.2 版本设备升级以后连不上平台怎么办？

检索过程可以是：

```text
1. 权限及有效性检查：只保留用户有权查看的现行文档
2. 元数据过滤：产品型号、适用版本 V3.2、维修手册
3. 关键词检索：升级、平台、连接
4. 语义检索：“连不上平台”≈“无法建立云端连接”≈“升级后离线”
5. 子块排序：优先匹配版本一致的故障原因和处理步骤
6. 父块回溯：恢复完整故障章节及关联表格、图片
7. 返回答案：处理方法＋文档名称＋版本＋章节＋页码
```

## 5. 常见错误

1. **只保存解析文本，不保存原文件**：无法回看原文或重新解析。
2. **旧版本与现行版本平等参与检索**：可能引用已经废止的制度或手册。
3. **整篇文档只生成一个向量**：内容过多，无法精确定位。
4. **机械地按固定字数分块**：容易拆散标题、条件、步骤和结论。
5. **为了保持完整而把知识块做得过大**：块内语义过多，向量匹配会变钝。
6. **只做向量检索，不做关键词检索**：错误码、型号和专业术语可能查不准。
7. **分块后不保留父节点、章节和页码**：无法恢复上下文和提供出处。
8. **把表格拉平成普通文本**：会丢失表头与单元格之间的对应关系。
9. **图片和流程图没有文字描述或多模态索引**：内容无法被有效检索。

## 6. 总结

> 非结构化数据录入时，应保存“原文件＋保真的解析内容＋完整元数据（含版本和有效状态）＋父子知识块”，同时建立全文、向量及必要的多模态索引；检索时先执行权限和有效性闸门，再在子块上进行混合检索，最后回溯父块补全上下文，并返回带版本、章节、页码和原文出处的答案。
