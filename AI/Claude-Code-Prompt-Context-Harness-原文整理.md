## 背景

原文从提示词工程(Prompt Engineering)、上下文工程(Context Engineering)和运行约束工程(Harness Engineering)三个维度分析 Claude Code。作者关注的不是普通前后端实现，而是 Claude Code 如何把基座模型组织成一个能够完成复杂、长程软件工程任务的 Agent 系统。

三者分别解决不同问题：提示词工程决定系统如何向模型表达任务和规则；上下文工程决定模型在当前阶段能够看到什么信息；Harness Engineering 则在模型之外提供工具、权限、执行循环、安全边界、钩子和验证机制。原文认为，最终效果并不只取决于模型能力，还取决于这三层工程设计能否协同工作。

# 提示词工程：静态信息与动态信息的组装

## 从“写提示词”转向“组装提示词”

Claude Code 的系统提示词(System Prompt)不是一段固定文本，而是根据用户、项目、会话、工具和运行环境动态拼装的结构。身份说明、系统行为、安全规则和工具规范相对稳定，可以作为静态部分；记忆、语言、环境、MCP、当前会话要求等信息会随任务变化，属于动态部分。

这种设计把提示词从单次编写问题变成了运行时组装问题。系统需要处理模块划分、优先级、缓存边界和上下文注入，而不是简单地把所有规则写进一段长文本。

## System Prompt 的组装流程

原文将主流程概括为：

```text
QueryEngine.ask()
  -> fetchSystemPromptParts()
  -> buildEffectiveSystemPrompt()
  -> query()
```

`fetchSystemPromptParts()` 并行获取三类信息：

1. `defaultSystemPrompt`：由 `getSystemPrompt()` 生成的默认系统提示词。
2. `systemContext`：由 `getSystemContext()` 获取的 Git 状态等系统上下文。
3. `userContext`：由 `getUserContext()` 获取的 `CLAUDE.md` 和当前日期等用户上下文。

默认系统提示词分为静态和动态两部分。静态部分主要包括：

- 身份介绍；
- 系统行为规则；
- 任务执行指南；
- 操作安全约束；
- 工具使用方法；
- 语气和风格；
- 输出效率要求。

动态部分位于 `__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__` 之后，可能包含：

- 会话级指导；
- 自动记忆；
- 环境信息；
- 语言偏好；
- 输出风格；
- MCP 服务器说明；
- 临时目录；
- 工具结果摘要策略；
- 长度锚点；
- 令牌(Token)预算及其他会话数据。

## 系统提示词的优先级

`buildEffectiveSystemPrompt()` 根据来源决定最终采用哪一套提示词。原文给出的顺序是：

1. `overrideSystemPrompt`：完全覆盖其他提示词；
2. Coordinator Prompt：协调器模式的专用提示词；
3. Agent Prompt：用户自定义 Agent 的提示词；
4. `customSystemPrompt`：通过命令行参数传入的提示词；
5. `defaultSystemPrompt`：默认系统提示词。

`appendSystemPrompt` 通常会追加到最终提示词末尾，除非系统处于完全覆盖模式。这个设计把“选择哪一套主提示词”和“追加补充规则”区分开来。

## 用户上下文和系统上下文的注入

系统会追加 Git 状态等系统信息，并把 `CLAUDE.md`、日期等用户上下文放入消息序列。原文特别提到，用户上下文不是随意混入普通文本，而是通过专用标签包装，从而让模型区分用户自然语言和系统注入信息。

## 缓存分块

系统提示词生成后会进一步拆分缓存边界。稳定前缀可以进入 KV 缓存(KV Cache)，会话动态内容则保持非缓存状态。这样做的目的，是在不牺牲动态性的情况下复用相同前缀，减少重复计算。

典型结构可抽象为：

```text
归属或计费头：不缓存
稳定系统前缀：组织级缓存
静态提示词：全局缓存
动态提示词：不缓存
```

## 系统提示词中的主要规则

原文列举了 Claude Code 系统提示词中的多组行为规则：

- 在修改代码前先阅读和理解现有实现；
- 优先编辑已有文件，避免不必要的新文件；
- 不对任务时长作没有依据的预测；
- 方法失败后先诊断原因，不机械重复，也不在第一次受阻时立刻放弃；
- 控制改动范围，不增加用户没有要求的功能、抽象和兼容层；
- 注意命令注入、跨站脚本(XSS)、SQL 注入等安全问题；
- 对不可逆、影响共享系统或对外可见的操作先确认授权；
- 优先使用与任务对应的专用工具；
- 独立工具调用尽量并行，有依赖关系的调用保持顺序执行；
- 用户可见文本应简洁、直接，并根据用户的技术水平调节解释深度。

原文还区分了外部用户和内部用户的沟通方式。外部版本强调减少铺垫和冗余；内部版本强调在关键节点提供完整、可恢复上下文的进度信息，使用户中途返回时仍能理解当前状态。

## 动态提示词模块

动态部分可能按会话启用不同模块：

- 会话指导根据当前工具和模式生成；
- 自动记忆通过 `loadMemoryPrompt()` 加载持久化信息；
- 环境模块描述工作目录、仓库状态、平台、Shell、操作系统和模型信息；
- 语言模块约束解释、注释和交流语言，同时保留技术名词与代码标识符；
- 输出风格模块注入用户配置的风格要求；
- MCP 模块加载服务器提供的使用说明。

## 子 Agent 的任务委派提示词

主 Agent 调用子 Agent 时，系统还会动态生成一份面向主 Agent 的使用说明。它需要告诉主 Agent：当前有哪些子 Agent、什么情况下应该自己处理、什么情况下适合委派、任务说明应包含哪些上下文，以及需要避免哪些错误的委派方式。

原文认为，多 Agent(Multi-Agent)架构降低了不同任务之间的上下文干扰，但也把一部分复杂度转移到了任务描述、信息传递和结果汇总上。因此，委派提示词本身也是系统能力的一部分。

# 上下文工程：引导、压缩和记忆

## CLAUDE.md 项目说明

`CLAUDE.md` 用于描述项目知识和行为规则，其内容会被加入用户上下文，并在会话早期提供给模型。它可以记录技术栈、架构、目录、编码规范、测试框架、常用命令和项目特有约束。

原文按作用范围列出四种位置：

- `~/.claude/CLAUDE.md`：保存个人通用偏好，跨项目生效；
- 项目根目录的 `CLAUDE.md`：保存团队共享规范，适合纳入 Git；
- `CLAUDE.local.md`：保存开发者在当前项目中的私有信息，不应提交到仓库；
- `.claude/rules/*.md`：按文件类型或业务领域拆分规则，并可通过前置元数据(Frontmatter)限制适用路径。

原文将 Claude Code 与私人助理类 Agent 作了对比：软件工程 Agent 更重视项目规则、代码结构和验证命令；私人助理类 Agent 则可能拆分身份、用户档案、工具、心跳和长期记忆等文件。上下文文件如何组织，应由 Agent 的任务定位决定。

## 三层渐进式压缩体系

长程任务会积累工具输出、代码片段和历史消息。原文将 Claude Code 的压缩策略分成三层：

1. 微压缩(MicroCompact)：不调用模型，使用规则处理旧的、体积较大的工具输出；
2. 会话记忆压缩(Session Memory Compact)：用已有会话记忆替换较早的消息；
3. 完全 LLM 压缩(Full LLM Compact)：调用模型生成结构化摘要。

### 微压缩

微压缩主要处理 Bash、Read、Grep、Glob 等容易产生大段标准输出的工具。Edit、Write 等代表状态变化的工具结果会被谨慎保留，避免压缩后丢失关键变更信息。

其执行路径包括：按时间截断旧工具输出，以及根据 KV Cache 边界只压缩缓存边界之外的内容。图片则使用固定 Token 数进行近似估算，以减少调度成本。

### 会话记忆压缩

当微压缩不足时，系统可以复用已有会话摘要，而不再发起一次新的模型总结。原文列出的默认策略包括：上下文达到一定规模且文本消息数量满足条件后才触发；限制单次压缩量；保留最近几轮消息，避免当前任务状态被旧摘要覆盖。

### 完全 LLM 压缩

前两层仍无法释放足够空间时，系统调用 LLM 对历史上下文进行结构化压缩。摘要模板覆盖：主要请求、关键技术概念、相关文件和代码、错误与修复、问题处理过程、用户消息、待办事项、当前工作和下一步。

压缩阶段会禁止模型调用工具，避免摘要任务产生额外副作用。模型先组织信息，再输出供后续会话使用的摘要内容。

### 自动触发

自动压缩(AutoCompact)在上下文剩余空间接近安全缓冲区时介入。系统优先采用不需要额外 LLM 调用的会话记忆路径；如果条件不满足或压缩效果不足，再回退到完全 LLM 压缩。这个顺序体现了成本、延迟和信息保真度之间的权衡。

## Memdir 结构化记忆

原文将 Memdir 的记忆分为四类：

- User：用户偏好和操作习惯；
- Feedback：历史纠错及行为反馈；
- Project：项目技术选择、架构决策和约束；
- Reference：可复用的文档、知识和代码模式。

`loadMemoryPrompt()` 负责扫描和分类记忆，并根据当前上下文预算裁剪后注入提示词。记忆规模较大时，系统还可以让模型参与相关性筛选，从候选内容中选择少量最相关记录，控制上下文体积和检索噪声。

# Harness Engineering：环境、约束与控制

Harness Engineering 指模型之外的运行环境和控制系统。接口、工具、钩子(Hook)、护栏(Guardrail)、权限、沙箱、执行循环和验证机制共同决定 Agent 能否在真实环境中稳定工作。

## System Reminder 动态注入

Claude Code 使用 `<system-reminder>` 标签包装配置、日期、工具结果和其他系统元信息。`wrapInSystemReminder()` 负责统一包装，`normalizeMessagesForAPI()` 在消息格式转换过程中执行标准化处理。

原文列出的应用位置包括：

- 会话开始前注入 `CLAUDE.md` 和日期；
- 工具执行后注入结果；
- 注入 Hook 的反馈；
- 注入待办状态、Skill 列表和可用 Agent 类型。

标签的作用是让模型区分用户输入与系统提供的运行信息，使动态上下文保持统一结构。

## 内置 AgentTool

### General-Purpose Agent

用于通用的复杂多步骤任务，拥有较完整的工具权限。其任务是完成目标，同时避免过度工程和半成品结果。

### Explore Agent

面向代码库搜索和调查，强调速度、只读和并行工具调用。它使用独立上下文消化大量搜索过程，只向主 Agent 返回结果，从而降低主上下文污染。原文提到，其搜索可分为快速、适中和全面三个程度；简单搜索直接使用 Glob 或 Grep 更合适。

### Plan Agent

用于实施前的代码库探索和方案设计。它保持只读，继承主 Agent 使用的模型能力，并要求输出关键实施文件。典型过程包括理解需求、研究已有模式、设计方案以及整理依赖和风险。

### Verification Agent

用于独立验证实现，而不是重复实现者的结论。它采用对抗式思路寻找缺陷，并针对不同变更类型选择验证方法：

- 前端变更：启动服务并进行浏览器验证；
- 后端或 API：调用端点并检查响应和异常处理；
- CLI 或脚本：验证标准输出、标准错误和退出码；
- 基础设施：执行语法检查和干运行；
- Bug 修复：先复现，再验证修复和回归；
- 数据库迁移：验证结构变化及回滚路径；
- 重构：要求既有测试不经修改仍能通过；
- 移动端：构建、安装并在模拟器中检查界面行为。

原文强调，验证不能停留在“代码看起来正确”或“实现者说测试通过”，而应运行实际检查并保留证据。

### Claude Code Guide Agent

用于回答 Claude Code CLI、Claude Agent SDK 和 Claude API 的使用问题。它会读取官方文档，并结合用户的 Skill、Agent、MCP 和设置生成回答。

### Statusline Setup Agent

用于配置终端状态栏，只需要有限的读取和编辑工具。它负责理解 Shell 配置，并转换为 Claude Code 的状态栏设置。

### Fork Sub Agent

这是一种继承父会话上下文的子 Agent。它可共享 Prompt Cache，限制返回格式和长度，防止继续递归 fork，并可在独立 Git worktree 中运行，避免文件改动直接影响主工作区。

原文认为，多种 Agent 的划分主要服务于四个目标：降低模型成本、实现最小权限隔离、减少主上下文污染，以及提高并行执行效率。

## 精细化安全体系

### 权限引擎

权限引擎(Permission Engine)在工具执行前进行规则判断，主要结果包括：

- Allow：低风险操作自动放行；
- Deny：明确禁止的操作直接拒绝；
- Ask：风险或意图不确定时请求用户确认。

规则可以来自全局设置、CLI 参数、命令规则和会话规则。系统按优先级合并这些来源，使默认安全策略和当前任务授权同时生效。

### 沙箱隔离

权限规则之外，系统还可以使用操作系统级沙箱(Sandbox)限制文件、网络、进程和用户权限。原文以 Linux 下的 `bubblewrap` 为例，说明只读根目录、白名单写入目录、网络和 PID 命名空间、非 root 用户等隔离方式。

沙箱不是固定应用于所有命令。对于交互式终端、特殊网络设备或与沙箱不兼容的命令，系统可能改用更严格的权限确认后直接执行。这是在隔离强度与命令兼容性之间做出的权衡。

## 异步生成器驱动的主循环

原文称 `queryLoop` 使用 `async function*` 构建主循环。异步生成器(Async Generator)允许系统在运行过程中持续 `yield` 事件，从而实现：

- 实时返回思考、工具调用和文件操作进度；
- 在关键节点暂停并等待用户确认；
- 通过 `return()` 取消任务并清理状态；
- 在多次 `yield` 之间维持局部运行状态。

主循环可概括为六步：消息预处理、调用 LLM、解析响应、执行工具及安全校验、产出事件、检查终止条件。

异常处理包括：上下文过长时触发压缩；输出达到上限时尝试续写；网络错误时采用指数退避(Exponential Backoff)。这一结构使 Agent 的执行过程可以被观察、暂停、恢复和终止。

## 可编程 Hook

Hook 覆盖工具、会话、消息和文件操作等生命周期，例如：

- `PreToolUse`、`PostToolUse`、`ToolError`；
- `SessionStart`、`SessionEnd`、`SessionPause`、`SessionResume`；
- `PreSampling`、`PostSampling`、`UserPromptSubmit`；
- `PreFileEdit`、`PostFileEdit`、`PreFileWrite`、`PostFileWrite`。

Hook 不只是接收通知，还可以返回结构化 JSON 来影响执行：阻断高风险操作、调整工具输入、清洗工具输出，或向会话注入反馈。配置可以在 `settings.json` 中通过工具匹配条件和外部命令声明。

由于 Hook 能执行外部代码，系统需要超时保护。原文提到工具 Hook 存在默认执行时限，超时后会终止脚本并返回错误，避免插件阻塞整个 Agent 主循环。

## 文章列出的产品彩蛋

### Caffeinate 防休眠

在 macOS 上，Claude Code 会通过 `caffeinate` 阻止空闲休眠。子进程采用短超时并周期续期，即使主进程被强制结束，防休眠状态也会在短时间后自动消失。

### 反蒸馏设计

原文提到两类做法：在服务端请求中使用与反蒸馏相关的工具定义策略；对 SDK 用户提供精简的工具执行摘要，并丢弃思考内容，减少完整执行轨迹暴露。

### 内部用户模式

内部环境会根据用户类型开启额外功能。例如提交代码时隐藏 AI 相关标记；通过内部使用(Dogfooding)持续验证产品；识别用户负面表达并触发反馈收集；对“continue”等续写指令做更严格的语义判断。

### 加载动词和 Buddy System

终端等待动画会随机显示大量非常规英文动词，使长任务的等待状态不只呈现统一的 Loading 文案。

`/buddy` 功能则提供 ASCII 电子宠物。宠物的种类、稀有度、外观和部分属性根据用户 ID 确定性生成，相同用户会得到相同结果；名字和性格由模型在首次创建时生成并保存。原文将这些功能视为产品文化的一部分：它们不影响核心任务执行，但增加了命令行工具的辨识度和陪伴感。

# 原文结论

原文最后将 Claude Code 的能力归因于多层工程协作：System Prompt 通过模块化和优先级进行动态组装；上下文压缩与记忆系统支持长程任务；权限、沙箱、工具、验证、主循环和 Hook 约束 Agent 的执行过程。

文章认为，构建 Agent 系统不能只关注模型和提示词。模型能力需要通过上下文管理和运行环境转化为稳定、可控的任务执行能力。Claude Code 的实现细节可以作为 Agent 系统设计的参考，但原文中的分析基于公开资料和作者个人实践，仍需要结合版本和具体场景验证。
