# Claude Code 的 harness 实现解剖

这篇是 [Harness工程.md](Harness工程.md) 的姊妹篇。那篇讲"为什么"(harness 工程是什么、四条原则、常见做法),这篇讲"怎么做"——拿一个真实的 harness(Claude Code)拆开看,它在提示词、上下文、运行约束三层各自落地成了什么样。

> 来源:阿里云开发者社区《深度解析 Claude Code 在 Prompt / Context / Harness 的设计与实践》(作者:飞樰,2026-04-23)。
> **重要前提**:下面这些实现细节是作者基于公开资料和逆向分析得来的,**不是官方文档确认的**,而且会随 Claude Code 版本变化。所以读的时候都默认带一句"据该文分析";要照着做之前,得结合你手上的版本自己验证。

一句话先把全貌说清楚:Claude Code 把一个基座模型,用三层工程包成了能干长程软件任务的 Agent——**提示词层**决定怎么向模型表达任务和规则,**上下文层**决定模型当前能看到什么,**Harness 层**在模型之外管工具、权限、执行循环和验证。最终效果不只看模型多强,更看这三层能不能协同。

# 一、提示词工程:从"写提示词"到"组装提示词"

最核心的一个转变:Claude Code 的系统提示词(System Prompt)**不是一段写死的文本,而是每次运行时按用户、项目、会话、工具、环境拼装出来的**。这更像搭积木而不是写作文——身份、安全规则、工具规范这些稳定的部分是固定积木,记忆、环境、语言、当前会话要求这些是随任务换的积木。(这个类比只说明"模块化拼装"这件事,别理解成积木之间没有顺序和优先级——下面就会看到优先级恰恰是关键。)

## 组装流程

据原文,主流程大致是:

```text
QueryEngine.ask()
  -> fetchSystemPromptParts()     // 并行取三类信息
  -> buildEffectiveSystemPrompt() // 按优先级定稿
  -> query()
```

`fetchSystemPromptParts()` 并行拿三样东西:**默认系统提示词**(身份、行为规则、安全约束、工具用法等)、**系统上下文**(Git 状态等)、**用户上下文**(`CLAUDE.md`、当前日期等)。

默认系统提示词又分**静态**和**动态**两半,中间用一个边界标记 `__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__` 隔开:

- 静态部分(稳定、可缓存):身份介绍、行为规则、任务执行指南、安全约束、工具用法、语气风格、输出效率要求。
- 动态部分(随会话变):会话级指导、自动记忆、环境信息、语言偏好、输出风格、MCP 服务器说明、临时目录、令牌(Token)预算等。

## 优先级:选哪套主提示词

`buildEffectiveSystemPrompt()` 按来源决定最终用哪套,据原文顺序是:

1. `overrideSystemPrompt`——完全覆盖其它;
2. Coordinator Prompt——协调器模式专用;
3. Agent Prompt——用户自定义 Agent 的;
4. `customSystemPrompt`——命令行参数传入的;
5. `defaultSystemPrompt`——默认的。

另外 `appendSystemPrompt` 会追加到末尾(除非处于完全覆盖模式)。这个设计把"**选哪套主提示词**"和"**追加补充规则**"两件事分开了。

## 上下文注入与缓存分块

用户上下文(`CLAUDE.md`、日期)不是随便混进普通文本,而是用**专用标签包装**后放进消息序列,好让模型分得清"哪些是用户说的、哪些是系统注入的"。

提示词生成后还会按**缓存边界**切块,目的是复用相同前缀、少算重复内容。抽象出来大概是:

```text
归属/计费头   : 不缓存
稳定系统前缀  : 组织级缓存
静态提示词    : 全局缓存
动态提示词    : 不缓存
```

稳定前缀进 KV 缓存(KV Cache),会话动态内容保持不缓存——**在不牺牲动态性的前提下省算力**。

## 系统提示词里的主要行为规则

据原文,Claude Code 的系统提示词里写了这些规则(挑几条有代表性的):改代码前先读懂现有实现;优先改已有文件、别乱建新文件;不对任务耗时做没依据的预测;方法失败先诊断、不机械重复也不一受阻就放弃;控制改动范围、不加用户没要求的功能和抽象层;注意命令注入、跨站脚本(XSS)、SQL 注入等安全问题;不可逆或对外可见的操作先确认授权;独立的工具调用尽量并行、有依赖的保持顺序。

原文还提到对**外部用户**和**内部用户**的沟通要求不同:对外强调减少铺垫冗余;对内强调在关键节点给出完整、可恢复上下文的进度信息,好让人中途回来还能接上。

## 子 Agent 的委派提示词

主 Agent 要调子 Agent 时,系统会**临时生成一份给主 Agent 看的"派活说明"**:现在有哪些子 Agent、什么时候该自己干、什么时候适合委派、任务描述要带哪些上下文、要避免哪些错误派法。

原文的判断是:多 Agent(Multi-Agent)架构降低了任务之间的上下文干扰,但代价是把复杂度转移到了**任务描述、信息传递、结果汇总**上——所以这份委派提示词本身也是系统能力的一部分。

# 二、上下文工程:引导、压缩、记忆

## CLAUDE.md:项目说明书

`CLAUDE.md` 用来告诉模型项目的技术栈、架构、目录、规范、测试框架、常用命令和特有约束,会在会话早期注入。据原文,它按作用范围分四个位置:

- `~/.claude/CLAUDE.md`——个人通用偏好,跨项目生效;
- 项目根目录 `CLAUDE.md`——团队共享规范,适合提交 Git;
- `CLAUDE.local.md`——开发者在本项目的私有信息,不提交;
- `.claude/rules/*.md`——按文件类型/业务拆分规则,还能用前置元数据(Frontmatter)限定适用路径。

原文顺带做了个对比:软件工程 Agent 更看重项目规则、代码结构、验证命令;私人助理类 Agent 则可能把身份、用户档案、工具、心跳、长期记忆拆成多个文件。**上下文文件怎么组织,取决于这个 Agent 是干什么的。**

## 三层渐进式压缩

长任务会越积越多工具输出、代码片段、历史消息,撑爆窗口。据原文,Claude Code 的压缩分三层,**遵循一个原则:能用便宜手段就别上贵的**(便宜=不调模型,贵=调模型):

1. **微压缩(MicroCompact)**:不调模型,纯规则处理那些又旧又大的工具输出。主要压 Bash、Read、Grep、Glob 这类爱刷大段标准输出的工具;而 Edit、Write 这种代表"状态改变"的结果会谨慎保留,免得压掉关键变更。做法是按时间截断旧输出、只压 KV 缓存边界之外的内容,图片用固定 Token 数估算。
2. **会话记忆压缩(Session Memory Compact)**:微压缩不够时,**复用已有的会话摘要**去替换较早的消息,而不是再发起一次新的模型总结。默认会限制单次压缩量、保留最近几轮,避免当前任务状态被旧摘要盖掉。
3. **完全 LLM 压缩(Full LLM Compact)**:前两层还不够,才真正调模型,对历史做结构化摘要。摘要模板覆盖:主要请求、关键技术概念、相关文件和代码、错误与修复、处理过程、用户消息、待办、当前工作、下一步。压缩时**禁止模型调工具**,免得总结过程产生副作用。

**自动触发(AutoCompact)**:窗口剩余空间接近安全缓冲时介入,**优先走不调模型的会话记忆路径**,不行再回退到完全 LLM 压缩。这个顺序就是成本、延迟、信息保真度之间的取舍。

## Memdir:结构化记忆

据原文,Memdir 把长期记忆分成四类:

- **User**:用户偏好和操作习惯;
- **Feedback**:历史纠错和行为反馈;
- **Project**:项目的技术选择、架构决策、约束;
- **Reference**:可复用的文档、知识、代码模式。

`loadMemoryPrompt()` 负责扫描、分类记忆,再按当前上下文预算裁剪后注入。记忆多的时候,还会让模型参与**相关性筛选**,从候选里挑少量最相关的,控制体积和检索噪声。

> 一个能互相印证的点:我(写这篇笔记的 AI)此刻运行的环境里,记忆系统的分类就是 **User / Feedback / Project / Reference** 这四类,跟原文描述的 Memdir 一致。也就是说,这篇文章拆的,基本就是我正跑着的这个 harness——这点能给前一篇文档里"这篇文档本身就跑在 harness 里"那节当个实锤。不过仍按前提:这是行为层面的吻合,不代表我能确认它底层代码就是原文写的那样。

# 三、Harness:环境、约束、控制

这一层是模型之外的运行环境:接口、工具、钩子(Hook)、护栏、权限、沙箱、执行循环、验证机制,合起来决定 Agent 能不能在真实环境里稳定干活。

## system-reminder:动态注入的统一信封

Claude Code 用 `<system-reminder>` 标签把配置、日期、工具结果等系统信息统一包起来。据原文,它出现在这些地方:会话开始前注入 `CLAUDE.md` 和日期、工具执行后注入结果、注入 Hook 的反馈、注入待办状态/Skill 列表/可用 Agent 类型。作用和前面"专用标签包装用户上下文"一样——**让模型分得清哪些是用户输入、哪些是系统运行信息**。

## 内置的几种 Agent

据原文,内置 Agent 各管一摊:

- **General-Purpose**:通用多步任务,工具权限较全,目标是干完活又不过度工程、不留半成品。
- **Explore**:代码库搜索调查,强调快、只读、并行;用独立上下文消化大量搜索过程,只把结果回传主 Agent,**降低主上下文污染**。搜索还分快/适中/全面三档,简单的直接用 Glob/Grep 更划算。
- **Plan**:动手前的探索和方案设计,只读,继承主 Agent 的模型能力,要求输出关键实施文件。
- **Verification**:独立验证实现,**不是重复实现者的结论,而是用对抗思路找缺陷**。按变更类型选验证法:前端起服务过浏览器、后端调端点查响应、CLI 查标准输出和退出码、Bug 修复先复现再验回归、重构要求旧测试不改也能过,等等。原文强调:验证不能停在"代码看着对"或"实现者说测过了",得真跑、留证据。
- **Claude Code Guide**:答 Claude Code CLI / Agent SDK / API 的用法问题。
- **Statusline Setup**:配终端状态栏,只需有限读写权限。
- **Fork Sub Agent**:**继承父会话上下文**的子 Agent,可共享提示词缓存(Prompt Cache),限制返回格式和长度、禁止继续递归 fork,还能在独立 Git worktree 里跑、不直接动主工作区。

原文总结,这么多 Agent 的划分主要服务四个目标:**降成本、最小权限隔离、减少主上下文污染、提高并行效率**。

## 权限引擎 + 沙箱

**权限引擎(Permission Engine)** 在工具执行前判定,三种结果:

- **Allow**:低风险,自动放行;
- **Deny**:明确禁止,直接拒;
- **Ask**:风险或意图不明,问用户。

规则来自全局设置、CLI 参数、命令规则、会话规则,按优先级合并——让"默认安全策略"和"当前任务授权"同时生效。

权限之外还有**操作系统级沙箱(Sandbox)**。原文以 Linux 的 `bubblewrap` 为例:只读根目录、白名单写入目录、网络和 PID 命名空间隔离、非 root 用户。但沙箱不是无脑套在所有命令上——交互式终端、特殊网络设备、与沙箱不兼容的命令,可能改成"更严格的权限确认后直接执行"。这是**隔离强度和命令兼容性之间的取舍**。

## 异步生成器主循环

据原文,主循环 `queryLoop` 用 `async function*`(异步生成器,Async Generator)构建。好处是运行中能持续 `yield` 事件,于是可以:实时返回思考/工具调用/文件操作进度;在关键节点暂停等用户确认;用 `return()` 取消任务并清理;在多次 `yield` 之间保持局部状态。

主循环大致六步:**消息预处理 → 调 LLM → 解析响应 → 执行工具及安全校验 → 产出事件 → 检查终止条件**。异常处理:上下文过长就触发压缩、输出到上限就尝试续写、网络错误用指数退避(Exponential Backoff)。整套结构让 Agent 的执行**可观察、可暂停、可恢复、可终止**。

## 可编程 Hook

Hook 覆盖工具、会话、消息、文件操作的整个生命周期,比如 `PreToolUse`/`PostToolUse`/`ToolError`、`SessionStart`/`SessionEnd`、`UserPromptSubmit`、`PreFileEdit`/`PostFileWrite` 等。

关键是 **Hook 不只是收通知,还能返回结构化 JSON 来影响执行**:阻断高风险操作、改工具输入、清洗工具输出、往会话注入反馈。配置写在 `settings.json` 里。因为 Hook 会执行外部代码,系统给它设了默认超时,超时就终止脚本返回错误,**免得一个插件卡死整个主循环**。

## 几个产品彩蛋

原文还列了些不影响核心任务、但有辨识度的细节:macOS 上用 `caffeinate` 防休眠(子进程短超时+周期续期,主进程被杀后防休眠也会自动消失);服务端的反蒸馏策略、对 SDK 用户只给精简执行摘要;内部用户模式(提交代码隐藏 AI 标记、识别负面表达触发反馈收集);终端等待时随机显示的非常规英文动词,以及 `/buddy` 的 ASCII 电子宠物(种类/稀有度按用户 ID 确定性生成)。

# 小结

把三层串起来看:**提示词层**靠模块化 + 优先级做动态组装,**上下文层**靠三层压缩 + 结构化记忆撑住长程任务,**Harness 层**靠权限、沙箱、工具、验证、主循环、Hook 约束执行过程。三层缺一,模型能力都没法稳定转化成可靠的任务执行。

几条能直接借走的设计思路:

- 提示词当成**运行时组装**的对象,而不是一段写死的文本;把稳定部分和动态部分分开,稳定的进缓存。
- 压缩**分级、按成本递增触发**:能用规则解决就不调模型。
- 权限用 **Allow / Deny / Ask 三态** + 沙箱,默认安全和当前授权按优先级合并。
- 主循环做成**能 yield、能暂停、能恢复、能取消**的结构,执行过程才可控可观察。
- Hook 要能**回写影响执行**(而不只是收通知),并且必须有超时保护。

最后再强调一遍前提:以上都是据该文的分析整理,**非官方确认,且依赖具体版本**,当设计参考可以,落地前要自己验证。想看这些做法背后的"为什么",回到 [Harness工程.md](Harness工程.md)。
